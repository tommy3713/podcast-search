# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

股癌搜尋 (https://gooaye-notes.com): an unofficial site with per-episode summaries, timestamped transcripts and cross-episode Q&A for the podcast《股癌 Gooaye》. One package: a Next.js app (`src/`) and an ingest worker (`worker/`) sharing one SQLite database.

The v1 stack (Express + Elasticsearch backend, Next 14 frontend, Python ingestion, k8s/EC2) was removed; it lives at tag `v1-es-final`. The v1 episode JSON is kept locally in gitignored `notes/gooaye/`.

## Workflow

`main` only changes through pull requests merged on GitHub: a ruleset rejects direct pushes, and the `check`, `image (web)` and `image (worker)` checks must pass. Never commit to `main` locally.

1. Branch from an up-to-date main: `git switch main && git pull && git switch -c feat/<topic>` (prefixes `feat/`, `fix/`, `chore/`, `docs/`).
2. Before pushing: `npm run check`, then try the change in `npm run dev` (fixtures) or `DB_PATH=data/prod.db npm run dev` (live snapshot, `npm run db:pull` first). Untested UI or worker changes don't go in a PR.
3. Run `/code-review` on the diff and fix what it finds.
4. `git push -u origin <branch>`, `gh pr create` (fill in `.github/pull_request_template.md`: how it was tested, whether the worker or `deploy/` changed). The PR title becomes the squash commit on main, so write it as a conventional commit (`feat: ...`, `fix: ...`). Then stop: don't merge or enable auto-merge. The owner reviews and merges on GitHub.
5. Merging deploys automatically (see Deploy); the result arrives in Telegram. Then `git switch main && git pull`.

## Environments

- **Production** is the VPS. `deploy/compose.yml` sets `APP_ENV=production`; secrets are in `/opt/gooaye/web.env` and `worker.env`.
- **Local dev** is everything else: no `APP_ENV`, secrets in gitignored `.env.local` (see `.env.example`). `src/lib/env.ts` `isProduction()` gates what must only happen live: R2 backups are skipped, Telegram messages are prefixed `🧪 DEV`, and the header shows a DEV badge.
- Local keys must be dev-only: an OpenAI project key with its own budget, a separate Telegram bot (only one process may poll a bot, and production's worker already polls the live one), no R2 credentials.
- Databases: `data/dev.db` (fixtures, `npm run dev:seed`) or `data/prod.db`, a snapshot of the live database without `ask_log` / `ask_usage` (`npm run db:pull`, then `DB_PATH=data/prod.db npm run dev` or `DB_PATH=data/prod.db npm run worker -- ...`). Nothing local ever writes to the live database.

`.npmrc` sets `legacy-peer-deps`; vitest is pinned to 4.x because npm 10.9 crashes on vitest 5's peers. Dependencies use exact versions.

## Architecture

### Database (`src/lib/db.ts`)

SQLite via better-sqlite3 plus the sqlite-vec extension; migrations run in `openDb(..., { migrate: true })`, which only the worker does. Tables: `episodes` (status `pending → transcribing → summarizing → done | failed`, `segments_json`, `summary_json`, `summary_draft_json`, `failed_step`, `cost_usd`, `source` `rss | backfill`, `seek_json`: see Seeking), `chunks` + `chunks_fts` (FTS5 trigram) + `chunks_vec` (vec0, 1536 dims), `summary_points` + `summary_points_vec` (one row per non-ad chapter and per key point, with the chapter's time span; only for ranking chunks), `mentions` (category, name, code, detail, quote, start_sec), `ask_usage`, `ask_log` (question, answer — as the page showed it, episode labels included, since the release that added them —, `outcome`, cited sources, tool calls, ms, tokens, cost; purged after 30 days), `ask_daily` (per-day totals rolled up from `ask_log`, kept forever), `worker_state` (key/value the worker keeps across restarts).

vec0 rowids must be bound as `BigInt`. Trigram FTS needs 3+ characters, so shorter search terms fall back to `LIKE` (`src/lib/ask/search.ts`).

The web reads through `readDb()` (readonly) and writes only `ask_usage` / `ask_log` through `writeDb()` (`src/lib/server-db.ts`).

### Worker (`worker/`)

`pipeline.ts` processes one episode in three checkpointed steps, each saved before the next starts, so a retry resumes from `failed_step` and never pays for a finished step twice:

1. **Transcribe** (`audio.ts`, `transcribe.ts`): download from RSS (needs a browser-like User-Agent or SoundOn returns 403), compress and split with ffmpeg, Groq `whisper-large-v3`. Gaps of 12 s+ in the result are re-transcribed on their own (Groq drops windows); a window counts as silence only when `no_speech_prob > 0.6` and `avg_logprob < -1`. `text.ts` converts with OpenCC `s2tw` (not `s2twp`) and applies known misheard-term fixes.
2. **Summarize** (`summarize.ts`): one gpt-5.5 call → `LlmSummary` (zod, `src/lib/summary.ts`): one-line summary, key points, chapters, stocks, mentions (food, sports, travel, media, games, products). `sanitizeSummary` caps lengths and drops out-of-range timestamps. Ads and non-investment brands are kept out of `stocks`.
3. **Embed and publish** (`chunk.ts`, `embed.ts`, `repo.ts`): ~600-character chunks on segment boundaries (adjacent chunks share a segment) and the summary points (`summaryPoints`: each non-ad chapter's title and bullets as one text, each key point, both spanning their chapter), embedded together with `text-embedding-3-small`, then one transaction that swaps the episode live. Live episodes whose summary points are missing or out of date (published before they existed, or re-run by the previous release during a deploy or a rollback) are fixed by `indexSummaries` (`summary-index.ts`: compares the stored points with what `summaryPoints` gives, embeds several episodes per request, and leaves a failed request's episodes for next time), which `run` queues at startup without waiting for it. Re-running a live episode keeps the old version visible until the new one publishes; a failed re-run leaves it untouched.

`schedule.ts`: RSS is polled every 30 min, 10:00–23:30 Taipei, on Wednesdays and Saturdays (release days); `nightly` runs at 03:00 (ask-log purge after `ASK_LOG_DAYS` = 30 days, gzip backup to R2 under `backups/`, deleted by a bucket lifecycle rule after 30 days). Questions really are gone after `ASK_LOG_DAYS`, as `/about` and `/ask` tell users, text included: a DELETE leaves it in free pages and in stale copies from page splits made while rows were inserted (`secure_delete` doesn't cover those), so nightly runs `VACUUM` when the purge removed rows and truncates the WAL every night, reporting a truncate a reader blocked (`compactDb`), and backups carry no `ask_log` rows (`stripAskLog`: DELETE + VACUUM on the journal-less copy), so a restore starts with an empty log. `tests/ask-log-privacy.test.ts` checks the raw files. `ASK_LOG_DAYS` (`src/lib/ask/quota.ts`) feeds the purge, `/stats`, the Telegram texts and both pages.

Monitoring (`monitor.ts`, `backup.ts`): the worker's own Telegram messages can't report the worker or the VPS being down, so external services watch too. A 30-minute timer pings `HC_HEARTBEAT_URL` (Healthchecks.io) unless the shared job queue has had one job running over 2 h (`MAX_JOB_MS`), so a dead process, a blocked event loop and a hung job (scheduled or from Telegram) all stop the heartbeat. Nightly checks free disk (below both 15% and 10 GB) and the live episode count against the highest seen (`<DB_PATH>.backup-state.json`; a drop is reported every night until that file is deleted), then backs up after `integrity_check` on the copy; any problem goes to Telegram and `HC_BACKUP_URL/fail`, success pings `HC_BACKUP_URL`. The worker posts `🔄 worker 已啟動` on every start. UptimeRobot checks the homepage for a keyword from outside. Pings never throw. Restore drill and procedure: `deploy/restore.md`.

Q&A stats (`stats.ts`): nightly rolls `ask_log` up into `ask_daily` before the purge (last 28 finished days only, so a thinned-out day is never rewritten); rows without an `outcome` (from before it was recorded) are left out. Telegram `/stats [days]` and a weekly digest (due from Monday 09:00 until sent; the week is remembered in `worker_state`) show outcome counts, cost, average time and the questions answered without a source.

`bot.ts`: Telegram commands `/status`, `/poll`, `/retry N`, `/resummarize N`, `/retranscribe N`, `/stats [days]`, `/questions [n]` (recent Q&A; `ask:<id>` buttons send one question with its answer, searches and cost), `/backfill [N|stop]`, and inline buttons (`action:N`). Only `TELEGRAM_CHAT_ID` is obeyed. All jobs run one at a time through `enqueue` in `actions.ts`. Success and failure notifications include the episode's running cost. `workQueue` (what polls and restarts pick up) runs newest first, so a new episode never waits behind retries of old ones, and leaves out `source = 'backfill'` episodes.

Backfill (`backfill.ts`): RSS polls only add episodes newer than the newest one; older ones are added by hand. `/backfill N` plans the N newest feed episodes below the newest one in the database that it lacks, or that a backfill added but didn't get live (with a contiguous database: the N below its oldest one), shows an estimated cost, and starts only from its confirm button (`backfill:<N>:<first>`, which plans again and checks it still starts there; at most 200). The planned list and its position are kept in `worker_state` (`backfill`), so a restart carries on with the episode it was on (`run` and a bare `/backfill` both call `runBackfill`). Each episode is its own queue job, newest first, with a two-minute pause before the next, so polls and commands get in between and a deploy finds the worker idle. The feed is read again for each episode (`addFromFeed` also refreshes a non-live row's audio URL); an unreadable feed counts as a failure and the same episode is tried after the pause. Episodes are added with `source = 'backfill'`: successes send no message, failures are reported by the pipeline and wait for the next `/backfill` instead of being retried by polls. Two failures in a row stop the backfill, and so do two episodes in a row that can't be added (missing from the feed, guid taken; otherwise skipped). One summary, with what this run spent, goes out after the last episode. Rolling back to a release from before `source` existed makes polls retry failed backfilled episodes like any other (up to 3 times each). `/backfill stop` ends it after the episode in progress. The CLI `backfill <n>` does the same without pause or confirmation; it is for local use only, since in production it would run beside the worker's own queue.

Seeking (`seek-table.ts`, `seek-index.ts`, `src/lib/seek.ts`): SoundOn's MP3s are VBR with a Xing table of contents (100 byte positions rounded to 1/256 of the file), browsers seek by it and then count `currentTime` on from the time they meant to reach, so after a click on a timestamp the transcript ran ahead of the voice. Measured on EP699 against the decoded audio, on a fresh element or right after `load()`: Chromium (`entry`) jumps to the entry at or before t and plays t + `offsets[i]` (−16.9 s at 40:30, up to ±19 s; model within 0.07 s at 4 points); Safari on macOS (`interp`) interpolates a byte position between the entries and plays from there (40:30 plays 40:14.9; model within 0.16 s at 5 points). `SeekTableParser` reads an episode's audio once and works out where the interpolated byte position at every 0.1% really falls; `seek_json` holds `{ duration, offsets }`, 1001 offsets (`offsets[k]`: where a seek interpolated to k/1000 of the duration plays, less that time; TOC entry i is point 10 i, so both models read the same array; about 5.5 KB per episode; `{ duration: 0, offsets: [] }`: CBR, no table, or a table without its byte count or that goes down, nothing to correct; NULL: not done yet; any other length is an older format, which the web ignores and `startSeekIndex` redoes). The transcribe step works it out from the audio it downloaded anyway (so a re-transcribed episode gets its file's table). `startSeekIndex` only fills live episodes lacking it (published before this, or by the previous release during a deploy), newest first, off the job queue (it only writes that column, and a backlog of downloads must not hold up polls or a deploy waiting for an idle queue), at startup and whenever the queue goes idle, but only while no job is queued and no backfill is under way: it stops before the next episode when either comes along (the one being read is finished), so its downloads don't compete with a job's, and the next idle queue starts it again. A failed download is tried next time, at most 3 times per worker start. The web reads `seek_json` only when the column exists, so an older snapshot still works.

### Web (`src/app`)

- The player (`EpisodeView.tsx`) works in audio time. `seekModel` picks `entry` for Chromium (`navigator.userAgentData`) and `interp` for Safari on macOS; browsers not measured are left alone (Firefox, every iOS browser, iPadOS (it sends the Mac user agent, so `maxTouchPoints`), WebKit on Linux), since correcting one that seeks some other way would add an error. With a model, a seek to x sets `currentTime` to `seekTarget(x)` (lands on x, or just before it where no seek reaches) and the shown time and transcript use `currentTime + offset`. Where a seek lands also depends on what the element has read (Chromium indexes read packets with the offset of the seek that led there: +30 s after 40:30 played 17 s early; Safari seeks a played element by average bitrate), so every seek on a loaded element first calls `load()`, making each one a fresh element's first seek, and timeupdates are ignored until it lands (`seeked`; a browser that dropped the seek shows `currentTime` uncorrected from `playing` on). A seek that didn't go through `seek()` gets the entry model in Chromium and no offset in Safari (which seeks a played element by average bitrate, a few seconds off at most). `setPositionState` gives the lock screen the audio time. The slider seeks on release, not while dragged. The OS media controls' seeks go through `seek()` via `mediaSession`. Measured through the page, three seeks in a row (a timestamp, +30 s, −15 s) land within 0.06 s in Chrome, and in Safari on macOS each inside the pause it was aimed at (0.02 s off where the audio allows telling). iOS can be measured in the Simulator (safaridriver with `safari:useSimulator`, `com.apple.WebInspector` `RemoteAutomationEnabled` in the simulator), but audio needs a real tap there.

Token use comes from the `AskTrace` that `answer()` fills in (only finished model turns report usage, so a timed-out or aborted request's cost is a lower bound); prices and `askCost` are in `src/lib/cost.ts`, shared with the worker. - `src/lib/ask/agent.ts`: Responses API tool loop (`ASK_MODEL`, default gpt-5.4-mini; at most 4 tool calls; `store: false` with encrypted reasoning passed back). Tools `search_transcript` (keyword, chunk vectors and summary vectors, fused with RRF; the summary ranking takes the 10 summary points nearest the query and brings the chunk of each point's chapter nearest it, because the summary's written wording matches how listeners ask where the spoken transcript often doesn't; the model only ever sees and cites chunks) and `search_mentions` (category, keyword). Both take `episode` and `since` / `until` (Taipei days, both ends included, like the dates in the source labels), applied inside each query (the keyword read limit, sqlite-vec's KNN via `rowid IN`), so a scoped search reaches episodes the limits cut off unscoped: `search_mentions` returns the 30 rows from the newest episodes, and keyword search reads at most 200 chunks per term, also from the newest episodes (ordered by episode, not chunk id: chunk ids follow insertion order, and backfill inserts older episodes last), with ties going to the newer episode. Either tool tells the model when it hit its limit (a term that matched more chunks than one read takes, logged as `cut` in `ask_log`'s tool calls, or a full page of mentions), and `search_transcript` also tells it when no term of the query is in any transcript, summary point or mention searched (logged as `unmatched`; summaries and mentions count because their names are corrected where the transcript misheard them): the meaning-based rankings always return their nearest chunks, and asked about Rivian, which no episode names, the model presented EP706's Tesla Roadster as the answer. The note says a passage counts only if it has the name, another name for it or something that sounds like it, since a misheard name matches no keyword either; told only to check the passages were about it, the model still took the Roadster passage, which names no car, for Rivian. Only a query none of whose terms appear gets it: one with a common word besides the name (`Rivian 電動車`) doesn't, because queries worded another way often have a word the episodes don't use. The server numbers sources and opens each result's text with its own `[n]` and episode (`[3] EP712 2026-11-07｜…`; brackets in the text become full-width, `escapeSourceText`), because with them only in the tag's attributes the model often cited `[1]` for whatever it had read and put content under the episode the question asked about; the model may only cite `[n]`, and `render.ts` drops unknown numbers and allows only `- ` lists and `**bold**`. Each line that cites something opens with the episodes of the sources it cites (`labelBlocks` on the page, `labeledAnswer` as text), worked out from the citations rather than written by the model: asked to write them, it put the wrong episode on about 4% of answers (an EP662 passage under「EP656：」, or a source number matched to the wrong label among 8–30 results). The prompt tells it not to write a label; one it writes anyway at the start of a line is replaced, and prose opening with exactly the label's episodes loses them. `ask_log`, Telegram and the eval's judge get the labelled text. A turn with neither text nor a tool call (seen once in 159 eval runs) gets one retry with tools off and a server note asking for the answer; a second empty turn throws, so the route refunds and shows an error instead of an empty answer. `toInputItem` strips the SDK's `parsed_arguments` / `parsed` fields, which the API rejects as input.

### Prompt-safety rules (keep these when editing prompts)

- System prompt holds rules and server facts only; user input goes in the user role inside `<question>`, never concatenated into the system prompt. Transcripts are untrusted too (listener messages are read on air): tool results are wrapped in `<transcript>` / `<mention>` with `<>` escaped to full-width (`escapeTags`), and the prompt says tag contents are data. The most important rules go last.
- No market-sentiment tags, no bullish/bearish or 正面/負面/樂觀/保守 labels, no investment advice: only report what the host said and let listeners judge. Asked whether he is bullish or whether to buy, the answer has no summary of his stance at either end, only a list of what he said.
- No URLs in answers, even when asked. When nothing answers the question, the answer says so without citing and without switching to something similar (another company, another car).

## Deploy

- Traffic reaches the VPS only through Cloudflare. DNS for `gooaye-notes.com` and `www` is proxied (orange cloud), A records only (no AAAA: visitors still get IPv6 at Cloudflare's edge, and the VPS's IPv6 stays out of DNS). SSL/TLS mode is **Full (strict)**, so Cloudflare verifies Caddy's Let's Encrypt certificate. **Always Use HTTPS is off** on purpose: Cloudflare forwards plain HTTP to Caddy, which answers ACME HTTP-01 challenges on port 80 and redirects everything else to HTTPS itself.
- A Vultr Firewall Group (outside the VM, so Docker can't bypass it the way it bypasses ufw) allows only TCP 80/443 from Cloudflare's ranges and TCP 22 from anywhere (SSH is key-only, root login disabled; GitHub Actions and a changing home IP need it). No IPv6 rules, so all inbound IPv6 is dropped. Connecting to the VPS IP directly on 80/443 times out; that is expected.
- Vultr VPS (Ubuntu 24.04, 1 vCPU / 2 GB). `/opt/gooaye` holds `compose.yml`, `web.env`, `worker.env` (chmod 600) and `data/app.db`; containers `web` and `worker`, no published ports.
- Caddy is shared by every app on the VPS: its own compose project in `/opt/proxy` (`deploy/proxy/`, deployed with `deploy/proxy/deploy.sh`; `deploy/proxy/README.md` explains how an app joins it), the only container that publishes ports (80/443, reachable only from Cloudflare). Apps join the external docker network `proxy` under a unique alias (web is `gooaye-web`) and own their site blocks in `/opt/proxy/sites/<app>.caddy`; gooaye's is `deploy/gooaye.caddy` (TLS, security headers, www → apex), installed by `deploy/remote-deploy.sh` on each deploy.
- `.github/workflows/ci.yml` runs typecheck and tests, then builds both `Dockerfile` targets, on every PR (images not pushed) and on every merge to `main`, which pushes `ghcr.io/tommy3713/gooaye-{web,worker}` (`:latest` and `:<sha>`). Never build on the VPS.
- Merging to `main` deploys automatically: `ci.yml`'s `deploy` job calls `.github/workflows/deploy.yml` (also runnable by hand from the Actions tab with a commit sha, which is how to roll back). It SSHes in with a key whose `authorized_keys` entry is `restrict,command="/opt/gooaye/bin/deploy-hook"`, so the only input is a sha: `deploy/deploy-hook.sh` checks the commit is on main, then runs `deploy/remote-deploy.sh` from that commit. The key and the VPS host key are secrets of the `vps` GitHub environment (host in its `DEPLOY_HOST` variable), which only `main` may use. Rollbacks only reach commits that contain `deploy/remote-deploy.sh`; to go further back, revert in a PR.
- `remote-deploy.sh <sha>`: fetch and validate `compose.yml` + `gooaye.caddy` at the sha, pull images `:<sha>`, run `worker migrate` with the new image, replace web, reload Caddy, check the homepage from the VPS through Caddy without Cloudflare (`curl --resolve gooaye-notes.com:443:127.0.0.1`, 200 and `id="ep-list"` in the body, 12 tries 5 s apart; the episode list rather than the brand, because the page streams and the header and footer say 股癌 with a 200 even when the database is broken), then replace the worker once its queue is idle and it's not within a minute or two of a :00/:30 scheduler slot (the worker writes `data/app.db.queue.json` with `running` and `waiting`; without it, episodes mid-pipeline count as busy; waits up to 60 min, otherwise leaves the old worker and says so), keep the images web and the worker run plus the previous deploy's, write `TAG=<sha>` to `/opt/gooaye/.env` so manual `docker compose` commands use the deployed release, and report to Telegram with the worker's bot. A failure (including the site check) puts the previous compose file, Caddy site (reloaded) and web back, leaves `.env` on the previous `TAG`, checks the site again and reports the step and whether the old version answers; the workflow then fails. `.prev` files left by a deploy that was killed mid-way are deleted at the start, never restored. The public path through Cloudflare is watched by UptimeRobot, not by the deploy.
- **Migrations must work with the previous release**: they run before web is replaced, and the old worker may keep running on the new schema for up to an hour. Add columns and tables; never rename or drop in the same release.
- `deploy/deploy.sh [sha]` deploys by hand with your own key (default: the newest commit on main that has images), running this checkout's `remote-deploy.sh`, so a change to it can be tried before merging. It also installs `deploy-hook` on the VPS.
- `.dockerignore` is an allowlist; add new top-level source directories to it. `next.config.ts` forces sqlite-vec's platform package into the standalone output (tracing can't see it) and excludes `data/` and `.env*`.
- Never prefix secrets with `NEXT_PUBLIC_`.

## Testing

`tests/` covers RSS parsing, text cleanup, summary validation, scheduling, repo/pipeline checkpoints, web helpers, Q&A search/render, backup, and monitoring (pings, disk, backup checks). Tests use in-memory SQLite and stub every network call (OpenAI, Groq, Telegram, R2). `tests/remote-deploy.test.sh` runs `deploy/remote-deploy.sh` end to end against stub `docker`/`curl`, succeeding, rolled back after a failed site check (an error, or a 200 without the episode list; with the old release answering and not), and failing early next to an interrupted deploy's leftovers (part of `npm run check` and CI); run it after any change to the deploy scripts.

Q&A quality (`evals/`, `scripts/eval.ts`, issue #24) is checked by hand, not in CI, because it costs money and needs a key. `evals/golden.jsonl` holds questions with checks rather than answers (`evals/README.md`: fields, how to run, and the rules for writing questions that stay valid through backfill). `npm run eval` runs each one 3 times through `answer()` against `DB_PATH` (default `data/prod.db`), read-only and without quota or logging, and saves to gitignored `evals/results/`, comparing with `baseline.json` there (the first full run, then only `--set-baseline`: a regressed result must not become what the next run is compared with). `scripts/eval/`: `golden.ts` (zod schema; a hash of what a question is scored on), `run.ts` (one run, followed with `AnswerRecorder` like the site), `score.ts` (rule checks, pass / unstable / fail, comparison with the baseline; runs that errored fail their question but stay out of the rates), `judge.ts` (`JUDGE_MODEL`, default gpt-5.4, marks each point yes/no from the answer text alone; the answer goes in the user role inside `<answer>`, escaped), `support.ts` (`SUPPORT_MODEL`, default gpt-5.4-mini: for each citation, whether the cited passage talks about its line; reported as 出處正確率, not part of passing; the results keep the cited passages' text), `retrieval.ts` (`--retrieval-only`: the search functions with each question's `queries`, keyword only (no embeddings, so not the summary ranking), plus what lies past the search limits), `report.ts`. The site, `ask-cli.ts` and the eval share `ASK_TIMEOUT_MS`, `readCoverage` and `AnswerRecorder`, so the eval asks and counts citations the way the site does. A run also fails on a citation in a line that names episodes in its own text but points at a source from none of them (`misCitations`, reported as 出處對不上; it checks the answer as the page shows it minus the computed labels, so a label the model wrote and the page replaced doesn't count, while a paragraph naming EP708 above a list item citing EP709 still does). `expect_eps` is checked twice: among the sources the searches returned (retrieval hit rate) and among the sources the answer cites (what a run needs to pass). Exit 1 means a `safety` question failed or the regression warning fired (2+ questions that passed every run and now fail every run, or hit rate down more than 5 points; passing only some runs is listed, not counted, since it happens between two identical runs). A full run stops on a snapshot without the `summary_points` table and warns when live episodes lack points (`npm run worker -- index-summaries` with that `DB_PATH` fills them, about US$0.0001 per episode). Run it for changes to `src/lib/ask/`, the prompt or `ASK_MODEL` (both sides on the same snapshot) and after each backfill batch; `tests/eval.test.ts` covers the scoring with a stub client.
